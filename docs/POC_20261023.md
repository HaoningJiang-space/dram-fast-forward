# 严格等价 DRAM Fast-Forward PoC

日期：2026-10-23。代码：`src/dram_fast_forward/`。

## 结论

**同 row READ 的数学批量执行可行；本次真实 FFN 流量暂不支持优先开发完整多面体系统。**
最规则的百万请求 A 流量，循环 CPU 加速 **5.82×**，计入解析、初始化和进程退出后
**4.39×**。完整真实 FFN 窗口的严格批量覆盖率为 **0%**，而增量前置命令更新得到
**1.29×** 循环 CPU、**1.25×** 整进程 CPU 加速。后二者来自实际重跑，未复用旧计时。

这是仿真器主机运行时间的改进，**不是芯片 token/s 提升**。未修改生产 Dense 后端，
未改 DRAM 物理时序、带宽、刷新、地址映射和 FR-FCFS 决策；没有上 GPU、创建环境或接触 RTL。

## 固定配置与实验范围

参考是现有 native/Ramulator 的真实源码和编译依赖，不是另写的带宽模型。
原模型、controller、scheduler、refresh 和 memory system 私有复制到 Orion 后构建。
一个二进制保留 reference/event/incremental/symbolic 四种模式；源码和链接依赖哈希见
[`evidence/build_v10/manifest.json`](../results/20261023/evidence/build_v10/manifest.json)。

- D32 有效端点：两层，每 core 八个独立 bank channel；64 个 core 的真实窗口对应
  64 个 memory instance。每 channel 的 row 为 1 KiB，事务 256 B。
- DirectBankRow、Generic controller、FR-FCFS、AllBank refresh 保持不变。
- DRAM 400 MHz，RD 间隔 8 拍，read latency 23 拍，refresh 间隔 3900 拍。
- 这里是独立 TSV bank 通路，**不存在跨 bank 共享数据总线**。C 验证 bank 并行及各通路
  的时序，没有凭空加入共享总线竞争。
- 保留原队列 `size <= max_size` 的行为，默认 64 的队列实际可接受 65 项，没有借机修它。

完整配置及原配置身份在 [`evidence/dram.yaml`](../results/20261023/evidence/dram.yaml) 和
[`evidence/config_origin.json`](../results/20261023/evidence/config_origin.json)。

| 类别 | 实际输入 | 范围 |
|---|---|---|
| A | 同 bank/row 连续 READ，64 项突发、间隔 700 拍 | 1万、10万、100万 |
| B | 同 bank 交替两行 | 同上，symbolic 精确回退 |
| C | 八个 bank 交错 | 同上，symbolic 精确回退 |
| D | 混合读写、突发、跨刷新 | 同上，symbolic 精确回退 |
| E | native 实际 FFN 请求 | 1万/10万前缀、完整224,896项、100万周期扩展 |

A 的最长流量使用 **stride=0**。该物理 row 只有四个不同事务，不能把它描述成无限长的
不同地址连续访问。额外 `A_affine4` 测试 0/256/512/768 的正步长小段。
另测中途写请求、callback 产生后续访存、接纳回压，以及 20 个围绕刷新边界的随机种子。

E 来自真实宽度 FFN：三次 Up/Gate，M32/N1792/K8192、付费 core Split-K4，FP16/FP32。
原 fixture 路径中的 `attention_frontier_benchmark` 是历史测试框架名称；**该输入实际是 FFN**。
没有只用人工规则地址冒充真实流量。完整窗口共 224,896 项，其中 READ 211,456、WRITE 13,440。
E 的百万项结果是实测窗口的周期扩展，**不代表另跑了一次百万项 native 长工作负载**。

## 数学快路径与安全边界

对已经打开的 row，令当前时刻为 \(t_0\)，路径上 RD-ready 约束最大值为 \(R\)，
RD→RD 的最大约束为 \(\Delta\)：

\[
t_{\mathrm{first}}=\max(t_0+1,R),\qquad
t_i=t_{\mathrm{first}}+i\Delta,\qquad
d_i=t_i+L_{\mathrm{read}}.
\]

若最后发射为 \(t_{n-1}\)，对于 RD 更新的时序项 \(j\)：

\[
R'_j=\max(R_j,t_{n-1}+\mathrm{latency}(RD,j)).
\]

这不是无条件套公式。守卫要求：唯一忙碌 instance 中只有一个忙碌 bank；没有 active、priority
或写队列；目标行已打开；固定步长、到达次序单调；RD 不改变 row 状态；timing window=1，
无 sibling/blocked-offset；PRE 不能插进 RD 间隔；其他命令不能更早就绪；空闲 controller
读写模式已稳定。无法证明的情形使用原始逐拍路径。

批量区间严格停在外部新请求、刷新和观察 checkpoint 之前。闭环还停在最早可能产生新请求的
回调之前。aggregate timing/history 只更新一次，但每个请求、命令可观察事件和完成回调仍
逐项保留；没有声称可把外部反馈成本变成 O(1)。

开放环中回调只记录完成；闭环测试允许回调产生访存。任意读取所有中间 DRAM 内部字段的
用户回调不属于这个 PoC ABI。当前充分守卫只对冻结模型成立，不是所有 Ramulator 配置的证明。
完整实现与复现命令见 [实验 README](IMPLEMENTATION.md)。

## 精确性验收

每个 case 首先记录 symbolic 实际退出拍；再令 reference/event/incremental 在相同拍观察状态。
比较的是原始数据，不是仅比较平均值或哈希：

1. 每条命令的类型、顺序、地址、发射拍。
2. 每次请求接纳/拒绝及重试拍。
3. 每个请求实际 callback 拍及身份，包含回压与闭环新增请求。
4. 每次 fast exit 的逐字段状态：全部队列请求、读写模式、row-hit/miss/conflict、刷新时钟与
   deadline、所有 DRAM node 的行状态、ready clocks 和 command history。
5. synthetic 的付费混合恢复后状态；E 排空后的状态。

原始事件流逐字节比较，所有 fast exit 的完整 JSONL 状态逐字节比较；SHA 只用于索引。
五类规模矩阵、完整真实窗口及额外边界共 20 case，另有 20 个随机种子，合计 **40 case 全部通过**。
主矩阵比较了 **21,977 次 fast-exit 完整状态**，随机检查额外执行 2,166 次批量 READ。
最终轮复用初版已保存的 **reference 原始记录与状态**，要求输入及退出拍完全一致；
**没有复用初版性能数据**，四种模式都用最终二进制重新计时。

另外，完整 E 回放与真实 native 捕获进行了独立比较：64 个 instance、757,228 条事件，
命令/地址/拍、接纳拍、callback 身份和拍全部一致。仅在独立 instance 之间规范化宿主记录顺序，
每个 instance 内部的顺序不放宽。见
[`evidence/actual_native_replay_equivalence_v10.json`](../results/20261023/evidence/actual_native_replay_equivalence_v10.json)。
E 仍然是开放环；闭环证据来自独立的 callback-followup 和随机测试，不宣称完成整个 decoder 闭环迁移。

## 计时方法与主要结果

每模式三个新进程，执行次序正向/反向/正向；固定各自 CPU，低优先级，保留其他人的任务。
计时关闭事件文件及完整状态记录。分别记录循环 CPU、整进程 CPU、wall time；CPU 中位数用于
比较，wall 原值保留供审查。不同规模/CPU 的绝对值不作跨案例因果比较。
reference 和快路径都保留相同的命令/完成计数接口；这个比值相对于 PoC 内的 instrumented
reference，不是对未加观测钩子的完整 native/ASTRA 端到端速度承诺。

| 场景 | reference 循环CPU | event | incremental | symbolic |
|---|---:|---:|---:|---:|
| A，100万项 | 5.639 s | 2.826 s / 2.00× | 2.933 s / 1.92× | **0.968 s / 5.82×** |
| E，实际完整窗口 | 1.517 s | 1.460 s / 1.04× | **1.175 s / 1.29×** | 1.496 s / 1.01× |

A 的整进程加速为 4.39×；批量覆盖 99.716% READ，平均每段 57.89 项。
E 的整进程 incremental 加速为 1.25×；symbolic 没有执行任何批量，约 1% 的计时差异
不能解释成数学快路径收益。全部规模、边界和回退结果见
[完整实测表](../results/20261023/MEASUREMENTS.md) 和 [机器汇总](../results/20261023/evidence/summary_v10.json)。

增量版本只缓存 prerequisite command，依照 enqueue/priority/状态命令使缓存失效。
它没有缓存随时间改变的 ready 判断，也没有替换 FR-FCFS 排序。这是最小原型，不能冒称
完整的增量调度器。event 版本也只是保守 lookahead 原型，不代表事件驱动技术的最佳实现。

## 真实流量机会：三个数字不能混淆

| 统计 | 完整真实窗口结果 | 能说明什么 |
|---|---:|---|
| 每 bank 相邻 READ 的同 row 比例 | 81.56% | 地址局部性较好 |
| 每 bank 同 row READ 段 | 平均5.42，P50/P90=4，最长56 | 长段有限，没有≥100的段 |
| 已实现严格全局隔离守卫的执行覆盖 | **0%** | 当前 A-only 批量机制未用于 E |

实际命令层面，同 row、固定 8 拍间隔的段平均 5.06 项。再要求没有中间本 bank 到达，
平均降为 2.20；进一步禁止中间任何全局 callback，平均仅 1.004，最长 3。
后者属于长度≥2段的 READ 只有 1,248 项，占全部 READ 的约 0.59%。
这些是逐项加条件后的**机会筛选统计**，不是已经证明安全的覆盖；还没检查全部队列/模式守卫。

主要打断因素是不同 bank/instance 的穿插、密集新到达、读写切换、PRE/ACT 与刷新。
实际捕获包括 ACT 41,014、PRE 39,481、PREA 1,021、REFab 1,024；刷新没有被省略。
详细直方图和打断分类见 [`evidence/real_trace_locality.json`](../results/20261023/evidence/real_trace_locality.json)
和 [`evidence/real_command_windows_v2.json`](../results/20261023/evidence/real_command_windows_v2.json)。

0% 是**这个保守的全局守卫**在这一 FFN 输入上的结果，不是“多 bank 数学批处理没有机会”的结论。
独立 bank 的局部批量可研究，但需要能与其他请求及反馈交错，不能从 81.56% 直接推算加速。

## 哪种开销更值得处理？

完整 E 窗口 reference 推进 9,878 拍。event 实际推进 8,613、跳过 1,265，只减少 12.81%；
高密度请求、命令和 callback 限制空拍收益，lookahead 本身还需要工作。
incremental 的 prerequisite 重算批次从 2,718,916 降到 294,086，避免约 89.18% 的重复重算，
实际循环时间下降约 22.55%。ready 比较、实际命令、回调、实例推进和其他成本仍在。
这里没有通过专用 profiler 把每项 CPU 成本完全拆开，不把计数比例冒充时间份额。

建议下一步优先把 **有精确失效规则的增量 prerequisite 更新**用于独立生产候选，随后优化
每 controller 的 next-event 维护；在真实闭环小图上重测。保留本批量路径作规则段机制证明，
暂不投入完整 polyhedral compiler 或 GPU。不得把三种独立模式的收益相乘。
